# 한국마사회 공공데이터 API 명세 (2026-10-18 기준, data.go.kr)

## ⚠️ 2026-10-18 실제 키 테스트 결과 요약

- **승인된 API는 3개뿐** (경주마 성적정보 / 경주마 레이팅정보 / 조교사 상세정보).
  "경주마 상세정보"(raceHorseInfo_2)는 이 키로 `SERVICE_KEY_IS_NOT_REGISTERED_ERROR`(403) —
  활용신청이 안 되어 있음. → **마주명/마주번호로 보유마를 자동 식별할 방법이 없음.**
  대안: 마주가 실제 보유마 수는 소수이므로, 마번/마명을 수동으로 입력해 관리하는 쪽이 현실적
  (아래 "보유마 식별 방식" 참고).
- **경주마 성적정보(raceHorseResult_2) API는 개발계정 트래픽이 하루 5회로 매우 적음.**
  테스트 중 바로 소진되어 `LIMITED_NUMBER_OF_SERVICE_REQUESTS_EXCEEDS_ERROR`(429) 발생.
  이 API를 제대로 쓰려면 data.go.kr에서 **활용사례를 등록하고 운영계정으로 트래픽 증량 신청**이
  필요함. 그 전까지는 하루 5회 한도 내에서 numOfRows를 최대한 크게 잡아 호출 횟수를 아껴써야 함.
  (타임아웃처럼 보였던 초기 증상도 동일한 서버단 트래픽 제한/부하 때문일 가능성이 있음.)
- **레이팅·조교사 API는 정상 작동 확인**, 아래에 실제 응답 필드명(영문 키)을 반영함.

공통 사항:
- 인증: 모든 요청에 `serviceKey` 쿼리 파라미터 필요 (공공데이터포털 발급 키)
- `meet` 코드 공통: 1=서울, 2=제주, 3=영남(부산경남+영천 통합 표출)
- 응답 포맷: JSON 또는 XML (`type=json` 파라미터로 보통 전환)

## 보유마 식별 방식 — ✅ 해결됨 (race.kra.co.kr 스크래핑)

애초 계획은 "경주마 상세정보" API(마주명/마주번호 포함)로 자동 식별하려 했으나 미승인 상태.
대신 **이 프로젝트는 조교사(마방) 기준으로 접근**한다 — 사용자의 보유마가 부산경남 11조
손병철 조교사 마방으로 들어가고, 이 도구 자체가 "조 단위로 출마투표 전 활용"하는 목적이기
때문에, 애초에 "마주 개인의 보유마"가 아니라 "마방 소속마 전체"가 분석 대상이 맞음.

`scripts/scrape_trainer_horses.py`로 race.kra.co.kr의 조교사 프로필 페이지(공개, 로그인 불필요)를
스크래핑해서 소속마 전체 현황을 가져온다. **공공데이터포털 API보다 오히려 더 유용함**:
- 서비스키/트래픽 할당량 제한이 전혀 없음 (공개 웹페이지)
- 마주명이 기본 포함 (API로는 막혀 있던 정보)
- 레이팅, 등급, 조번, 전적 요약까지 한 번에 제공

### 사용법
```
python scripts/scrape_trainer_horses.py --tr-no 070302 --meet 3
```
→ `data/processed/손병철_11조_소속마.csv` 생성 (2026-10-18 기준 28두 확인됨)

### 응답 필드
순, 마번, 마명, 마주명, 조번, 등급, 레이팅, 산지, 성별, 연령, 데뷔일자, 전적(총전/1착/2착/3착), 비고

### 내부 동작 (재현/유지보수용)
- `POST https://race.kra.co.kr/trainer/profileTrainerPersonItem.do` — 조교사 인적사항(성명, 소속조)
  - form data: `trNo`, `meet`, `Act=10`, `Sub=1`
- `POST https://race.kra.co.kr/trainer/TrainerTrustManagehorse.do` — 위탁관리말(소속마) 전체 목록
  - form data: `trNo`, `meet`, `Act=10`, `Sub=1`, `argOrderBy=0`
  - 응답은 `euc-kr` 인코딩, 소속마 테이블은 두 번째(더 큰) `<tbody>` 안에 있음
  - 마번은 각 행의 `goPage5('마번')` 자바스크립트 호출에서 추출

**리스크**: 비공식 스크래핑이라 KRA가 페이지 구조를 바꾸면 깨질 수 있음. 공개 웹페이지 조회이며
로그인/인증 우회가 아니므로 문제는 없으나, 과도한 호출은 피할 것(하루 1~2회로 충분).

## 말별 경주 이력(시계열) — ✅ 해결됨 (race.kra.co.kr 스크래핑)

"시계열 부재" 문제(공공데이터 API는 최근 1경주 스냅샷만 제공)도 같은 방식으로 해결함.
`scripts/scrape_horse_history.py`가 말 1두당 **경주성적 탭**(`/racehorse/profileRaceScore.do`)을
긁어서 경주별 전체 이력을 가져온다. 2026-10-18 기준 11조 28두 전체 수집 테스트 완료 —
총 300개 경주 기록 확보 (`data/raw/race_history/race_history_combined.csv`).

### 사용법
```
# 소속마 CSV 전체 일괄 수집
python scripts/scrape_horse_history.py --horses-csv "data/processed/손병철_11조_소속마.csv"

# 말 1두만 테스트
python scripts/scrape_horse_history.py --hr-no 0057801 --meet 3
```

### 응답 필드 (경주 1건당)
순, 경주일자, 경주번호, 출주번호(그날 게이트번호), 경주종류, 거리, 등급(그 경주 당시 등급),
순위(형식 "순위/출주두수"), 기수, 중량(부담중량), 레이팅(그 경주 당시 레이팅),
경주기록(시간), 마체중, 마체중증감, 주로(상태), 주로빠르기

**검증**: 게임메이커(0057801)의 공식 4전 기록이 소속마 CSV의 전적 "4(0/2/1)"과 정확히 일치
(9위→2위→2위→3위, 0승 2착2회 3착1회). 신뢰할 수 있는 데이터로 확인됨.

### 내부 동작 (재현/유지보수용)
- `POST /racehorse/profileHorseItem.do` — 마적사항(현재 스냅샷: 레이팅, 등급, 마주, 통산전적 등)
- `POST /racehorse/profileRaceScore.do` — 경주성적(경주별 시계열)
  - form data: `hrNo`, `meet`, `Act=08`, `Sub=1`
  - 응답은 `euc-kr`, 경주 목록은 두 번째(더 큰) `<tbody>`
  - 경주일자는 각 행의 `goScore("meet","date","rcNo")` 자바스크립트 호출에서 추출
  - 데뷔 전 모의/시범경주 등 일부 초기 행은 날짜 형식이 달라 rcNo 추출이 안 될 수 있음(raw 텍스트로 폴백)

### 이걸로 가능해진 분석
- **레이팅 추세**: 경주별 레이팅 값의 시계열 변화
- **출주 간격**: 연속 경주일자 간 차이(日)
- **조건 적합도**: 거리/등급/주로상태별 과거 순위 분포
- (상대전력 분석은 별도로 "이번 주 출전예정마" 데이터가 필요 — 출마투표 임박 시점에 추가 설계)

### ⚠️ 교류경주(타 경마장 원정) 처리 — 2026-10-18 수정
`profileRaceScore.do`는 말의 **전체 이력을 홈 경마장(meet) 구분 없이 다 반환**한다 — 즉 11조
말이 서울/제주로 원정 가서 뛴 교류경주도 원래 다 포함되어 있었는데, 처음엔 각 경주의
`goScore("meet","date","rcNo")`에서 meet 값을 버리고 date/rcNo만 썼다. 그 결과 서울 교류경주
우승 2건(판타스틱밸류, 2026-04-26·2026-09-20, 둘 다 1위)이 데이터에는 있었지만 구분이 안 됐음.

**수정**: `개최지`(서울/제주/부산경남/영천), `교류경주`(Y/홈경마장과 다르면) 컬럼을 추가해서
원정 경주를 명시적으로 표시하도록 고침. 11조 중 6두가 교류경주 경험 있음 (판타스틱밸류 4전2승
서울, 판타스틱킹덤 3전, 판타스틱포스 3전, 디스파이트윈 2전, 리치트리 1전, 판타스틱선더 1전 영천).

**의미**: 교류경주는 보통 다른 지역 최상위권 말들이 모이는 자리라 홈 경마장 등급 비교보다
수준이 높음 — 교류경주에서의 성적(특히 우승)은 "등급내백분위"가 못 잡아내는 추가 신호로
`analyze_entry_candidates.py`에 `교류경주참가`/`교류경주우승` 컬럼으로 반영함.

### ⚠️ 거리 미반영 버그 수정 — 2026-10-18
`class_percentile`이 처음엔 등급만으로 모집단을 걸렀음(거리 무시). 같은 등급이라도 거리가
다르면 체질이 다른 말들과 섞여 비교가 흐려짐 — 예를 들어 판타스틱킹덤은 "1등급 전체"
기준으로는 백분위 90.5%였지만, 실제 최근 출전거리(1200m)로 좁히면 70.0%로 내려감(여전히
상위권이지만 "전체 1등급에서 압도적"이라는 결론은 과장이었음).

**수정**: 등급+거리를 함께 매칭하되, 표본이 부족하면 단계적으로 완화 — ①등급+거리 정확히 동일
→ ②등급 동일 + 거리 ±200m → ③등급만(거리 무시, 표본 부족 명시). 결과 CSV의 `비교기준` 컬럼에
어느 단계로 계산됐는지 항상 표시됨(투명성 확보).

**한계 — 명확히 인지할 것**: 이건 "과거 12개월 동일 등급·거리 모집단 대비 통계적 위치"이지,
실제 그 경주에 나올 특정 상대마들과의 비교가 아님. 미래 출전 명단은 사전에 공개되지 않는다는 걸
이미 확인했으므로(위 "미래 경주 조건표" 관련 조사 참고), 이게 현재 공개 데이터로 할 수 있는
최선의 "상대적 경쟁력 추정"이다.

### ⚠️ 주로상태까지 추가 반영 — 2026-10-18
등급+거리에 더해 주로상태(건조/양호/다습/불량/포화)까지 맞추도록 확장. 매칭 우선순위:
①등급+거리+주로상태 동일 → ②등급+거리 동일(주로 무시) → ③등급 동일+거리±200m → ④등급만.

**버그 발견 및 수정**: 처음 구현에서 1단계가 단 한 번도 매칭되지 않았음 — 말 이력 쪽 주로상태가
"건조(4%)"처럼 함수율이 붙어있는데 모집단(race_meta) 쪽은 "건조"만 있어서 문자열이 절대 같을 수
없었음. 정규식으로 괄호 앞부분만 추출해 범주만 비교하도록 수정 후 대부분 말이 ①단계(등급+거리+
주로상태 모두 동일)로 매칭됨 — 예: 백투더드림 88.5%ile(건조, 182표본), 퀸메이커 9.1%ile(양호,
11표본, 거리 무시했을 때 17.6%ile이었던 것보다 더 하위로 나와 더 정밀해짐).

## 부산경남 전체 경주결과 (타 마방 포함 비교용) — ✅ 수집 중 (2026-10-18)

11조 소속마만으로는 "이 레이스가 유리한가"를 판단할 수 없음 — 같은 등급이라도 그날 어떤
말들이 나오느냐에 따라 승산이 달라지므로, **부산경남(meet=3) 전체 경주결과**를 모집단으로
확보해야 함. `scripts/scrape_race_results.py`가 경주일자 단위로 그날 열린 전체 경주의
전체 출전마 결과를 수집한다 (특정 마방에 한정되지 않음 — 레이스 1건 = 모든 마방의 말 포함).

### 데이터 소스 (race.kra.co.kr, 공개, 로그인 불필요)
- `POST /raceScore/ScoretableScoreList.do` (pageIndex 페이지네이션) — 날짜 목록. **주의**: meet=3(부산경남)과
  meet=4(영천)가 섞여 나옴 — "영남경마"로 통합 표출되는 것과 같은 현상. meet=3만 필터링해야
  순수 부산경남 데이터가 됨.
- `POST /raceScore/ScoretableDailyList.do` — 그날 열린 경주번호 목록
- `POST /raceScore/ScoretableDetailList.do` — 경주 1건의 전체 출전마 결과 + 경주 메타정보

### 수집되는 필드
**경주 메타** (`race_meta_3.csv`): 경주일자, 경주번호, 경기장(부경/제6경주 등), 날씨, 주로상태,
**함수율(%)**, 출발시간, 등급, 거리, 부담종류, 경주명, 레이팅조건, 연령조건

**출전마 전체 결과** (`race_field_3.csv`, 경주당 8~14행): 순위, 출주번호, 마명, 마번(hrNo),
산지, 성별, 연령, 중량, 레이팅, 기수명, 조교사명, **마주명**, 도착차, 마체중, 마체중증감,
단승/연승 배당, 장구현황

→ 마주명·조교사명이 행마다 포함되어 있어 **다른 마방 말도 자동으로 모집단에 들어옴** — 이게
핵심. 11조만 수집할 때보다 훨씬 유용함.

### 증분 수집 설계
`data/processed/race_results_state.json`에 이미 수집한 날짜를 기록 → 다음 실행부터
`--incremental` 옵션으로 새로 열린 경주만 추가. **최초 1회만 과거분을 백필(예: 12개월)하면
그 뒤로는 빠르다** — 이게 이 프로젝트의 핵심 설계 원칙.

```

python scripts/scrape_race_results.py --months 12

# 이후 (매주 1회 정도) 증분 수집
python scripts/scrape_race_results.py --incremental
```

### 이걸로 추가 가능해지는 것 — "보정 기록(스피드 피규어)" 설계의 재료
- **주로/거리별 기준기록(par time)**: 같은 거리+주로상태(함수율 구간)에서 뛴 전체 출전마의
  기록을 모아 그 조합의 "평균 기록"을 산출 → 날짜/장소에 따른 주로 컨디션 차이를 제거
- **부담중량 보정**: 중량과 기록의 관계를 회귀분석해 "동일 중량 기준" 환산
- **등급 간 격차 보정**: 레이팅조건(R0~140 등)과 실제 레이팅 분포로 등급 간 수준차 추정
- **상대전력 분석**: 마주명/조교사명이 포함돼 있어 "이 등급·거리에 다른 마방 말들이 최근
  얼마나 잘 뛰었는지" 비교 가능 → 11조 말을 넣었을 때 상대적 위치 추정
- **상금 기대값(EV)**: 경주 메타에 순위상금/부가상금 구조가 포함돼 있어 등급별 기대수익 계산 가능

## 데이터 설계 상 시사점

1. **시계열 부재 문제**: API들은 "현재 스냅샷" 위주라, 레이팅 추세·출주 간격 패턴을 보려면
   주기적으로(예: 매일 또는 경주일마다) 호출해서 `data/raw`에 날짜별로 누적 저장해야 함.
   과거 데이터가 없으므로 **지금부터 수집을 시작해야 쌓인다** — 가능하면 오늘부터 일 1회 수집 스케줄링 권장.
2. **부산경남 특정 필터**: `meet=3` (영남, 부산경남+영천 통합)로 보이나, 레이팅 API는 meet 파라미터를
   무시하고 전체를 반환하는 것으로 관찰됨(미확정) — 응답의 `meet` 필드값으로 사후 필터링 필요.
   영천경마와 혼합 표출되므로, 분석 시 "진짜 부산경남 개최"인지 레이스명/경기장 필드로 재확인 필요.
3. **보유마 식별**: 위 "보유마 식별 방식" 참고 — 수동 CSV 기반.
4. **레이팅 4종(rating1~4)의 정확한 의미**는 문서에 명시 안 됨 — 같은 마번을 여러 날짜에 걸쳐
   수집해서 어떤 값이 변하는지로 역추적 필요 (예: rating4가 "최신 공식 레이팅"일 가능성 높음 —
   레이팅 범위가 더 넓어 보임).
5. **경주마 성적정보 API는 개발계정 트래픽 5회/일로 매우 빠듯함.** 운영계정 승격(활용사례 등록)
   전까지는 numOfRows를 크게(예: 500~1000) 잡아 한 번의 호출로 최대한 많은 행을 받아오는 방식으로
   설계해야 함 — 마번별로 쪼개서 호출하면 바로 한도 초과.

## 거리별 분해(distance_breakdown.py) — 등급 미분리 버그 수정 (2026-10-18)

처음엔 "거리"로만 묶어서 같은 거리의 출전 기록을 하나로 합쳤는데, 같은 거리라도 하위등급
때 뛴 기록과 승급 후 상위등급 때 뛴 기록이 섞여버려서 "하위군에서 압도적으로 이기다가
승급한" 케이스를 구분할 수 없었음. 거리+등급을 함께 묶도록 수정 — 승급 전/후 성적이 각각
별도 행으로 나뉨. 예: 디스파이트윈 1600M이 혼3등급(90.6%ile)→2등급(27.3%)→1등급(9.3%)→
혼OPEN(62.5%)으로 승급 과정이 그대로 드러남. 백테스트 스크립트들(`compute_percentile_asof`
기반)은 이 모듈을 쓰지 않으므로 이 수정으로 인한 재검증은 불필요함.

## OPEN은 등급이 아니라 "등급 제한 없이 뛰는 경주" (2026-10-20)

사용자가 "오픈은 등급이 아니라 등급 제한 없이 뛰는 경주 아니냐"고 질문 → 실측으로 확인.
같은 "국OPEN" 라벨이어도 경주마다 참가 레이팅 범위가 완전히 다름(한 경주는 55~109, 다른
경주는 31~50) — 반면 번호등급(1~6등급)은 날짜가 달라도 항상 같은 밴드. 즉 OPEN은 "그
경주에 레이팅 상한 없이 아무나 낼 수 있다"는 조건일 뿐, 실력 구간을 나타내는 등급이 아님.

고친 내용: `analyze_entry_candidates.py`에 `build_grade_ceilings()`(실측 데이터로 번호등급별
레이팅 상한표를 만듦)와 `infer_open_grade()`/`attach_matched_grade()`(OPEN 라벨을 그 상한표에
맞춰 실제 레이팅 기준 번호등급으로 치환)를 추가. `percentile_for_condition()`·
`rival_comparison.py`·`backtest_rating_percentile.py`의 등급 매칭 전부 이걸 거치도록 수정.
카드 배지는 실제 뛴 등급("국OPEN")을 그대로 보여주되, 상대마 비교 요약에는 "국3등급(OPEN환산,
원등급 국OPEN)"처럼 재분류 사실을 투명하게 표시. 백테스트(`compute_percentile_asof`)는
lookahead bias 방지를 위해 상한표도 `history_pool`(그 시점 이전 데이터)만으로 계산 —
load_population()처럼 전체 데이터로 만들면 미래 정보가 섞임.

재검증: Spearman -0.3175→-0.3149, 1위픽 승률 배수 2.03→2.11배로 핵심 지표는 그대로이거나
소폭 개선(OPEN 경주 비중이 전체의 ~3%뿐이라 당연한 결과).

## 상대마 비교에 레이팅 없는 말(신마·최하위군)도 순위없이 포함 (2026-10-20)

레이팅 없는 말(대부분 국6등급)이 `rival_comparison.py`의 모집단 구성 단계에서 통째로
걸러지고 있었음(`dropna(subset=["레이팅_num"])`). 사용자가 "순위 없는 말들도 아래쪽에
표시하면 좋지 않을까"라고 요청 → 레이팅 없는 말도 모집단에 포함하되 백분위/조합점수는
공란 처리, 정렬 시 판다스 기본 동작으로 맨 아래에 깔리도록 수정. 대시보드 쪽은 순위
"–"(em dash)로 표시, `render_unscored_card()`가 `build_detail_blocks()`에 빈 DataFrame을
넘기던 버그도 같이 고침(신마 카드엔 애초에 상대마 비교 섹션 자체가 없었음).

## 영천(meet=4) 경주를 부산경남 모집단에 합침 (2026-10-20)

사용자가 "10/18 경주가 공공데이터엔 없는데 마사회 홈페이지엔 있다"고 확인 요청 →
실제로는 데이터 수집 문제가 아니라 그 경주가 영천(meet=4)에서 열린 경주였음(부경은
10/16이 최신). `race.kra.co.kr`의 "영남경마" 메뉴가 부경(meet=3)과 영천(meet=4)을 한
화면에 섞어서 보여줘서 혼동이 생김 — 날짜별 개최지("영천"/"부경") 라벨로 구분해야 함.

사용자가 추가로 확인해준 사실: **현재 서울은 영천 경주 참가를 거부하고 있어서, 영천 경주는

경주"로 취급해 모집단에서 빼는 건 잘못된 가정 — 실제로는 장소만 다른 부산경남 경주로 봐야
함. 서울이 복귀하면 상황이 바뀔 수 있으므로, 그 경우엔 기존 "[서]" 접두사 방문마 필터가
자동으로 서울말을 걸러낸다(코드 변경 불필요).

고친 내용:
- `scrape_race_results.py` — meet별 상태파일 분리(`race_results_state_4.json`), meet=3은
  기존 상태파일 그대로 사용(하위호환, 중복수집 방지). `--meet 4`로 영천 수집 가능.
- `analyze_entry_candidates.py`의 `load_population()` — `race_meta_3/4.csv`+`race_field_3/4.csv`를

- `home_filter()` 신설 — 교류경주라도 개최지가 영천이면 "원정"으로 치지 않음
